# sctl Browser 第 4 期：调试

<!-- File: docs/specs/2026-10-04-browser-debugging.md -->

> Status: Approved
> Owner: sctl maintainers
> Last updated: 2026-10-08

**目标：** AI agent 和 shell 脚本可以通过 sctl 命令行和 MCP，读取用户浏览器里某个标签页的控制台输出、JS 异常、浏览器警告和网络请求，并且可以先开始录制、让用户复现问题，之后再查询。

**不可退化的约束：**

- 第 1–3 期的全部行为不变：ScriptCat 的连接和 `scripts.*`、浏览器数据管理命令、页面自动化命令、MCP 工具和退出码。
- 给 ScriptCat 的生成 TS 文件保持逐字节不变。

本期是五期规划中的第 4 期，依赖第 3 期的 CDP 中转（已合并）。

## 问题

1. **sctl 读不到页面的调试信息。** 已验证。
   - 第 3 期的页面自动化只在内部跟踪进行中的网络请求，用来判断 `networkidle`，不保存请求，也不处理控制台和异常事件（`internal/daemon/page/network.go` 的 `netWatch`；第 3 期 spec「不在本期范围」把调试数据留给本期）。
   - 用户让 AI 排查「页面为什么报错」「接口为什么失败」时，AI 只能 `page eval` 猜测，看不到控制台和网络。
2. **调试器附加时间太短，无法长时间观察。** 已验证。
   - daemon 在最后一条页面命令结束 5 分钟后断开调试器（`internal/daemon/page/manager.go` 的 `idleTimeout`）。扩展另有 10 分钟的兜底断开（`extension/src/handlers/debugger.ts` 的 `IDLE_DETACH_MS`）。
   - 「先开始观察，让用户操作复现问题，再回来看」这种用法做不到：用户操作期间没有页面命令，调试器会被断开。

## 角色与用户故事

1. 作为通过 `sctl mcp` 接入的 AI agent，我希望查看某个标签页的控制台错误和失败的网络请求，这样能定位用户报告的页面问题。
2. 作为 AI agent，我希望先开始录制，再请用户在页面上操作复现问题，之后只取新增的记录，这样不用反复拿到旧数据。
3. 作为 shell 脚本作者，我希望按状态码或 URL 筛选请求，并拿到某个请求的请求头、响应头和响应体，这样能写自动检查。

## 设计决策

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | 调试器附加期间始终缓存调试事件，无论附加由哪条命令引起；另提供显式的开始和停止录制，录制期间调试器不因空闲而断开。 | 用户决定。附加期间的事件是免费拿到的，丢掉可惜；显式录制满足「先录，用户复现，再查」。被否：只在附加期间记录、不提供录制，空闲 5 分钟后数据就没了；只在显式录制时记录，忘记先开始就什么都没有。 |
| 2 | 网络请求的列表只给摘要；单个请求的详情按需取，响应体要显式要求才取。请求头和响应头、请求体、响应体都原样返回，不打码。 | 用户决定。摘要让 AI 的上下文保持小；与第 2 期 Cookie 值不打码的决定一致，影响写进威胁模型。被否：打码 Cookie、Authorization 等头，调试登录问题时看不到实际值；只记录摘要，很多接口问题查不出来。 |
| 3 | 只提供查询，不提供持续输出。每条记录带递增的序号，结果返回下次续查用的游标。 | 用户决定。MCP 无法流式输出，AI 和脚本都用同一种轮询方式。被否：命令行另加 `--follow`，需要控制接口支持流式，工作量大。 |
| 4 | 录制中的标签页连续 60 分钟没有任何 `debug` 查询时，录制自动结束，之后回到正常的 5 分钟空闲断开。 | 用户决定。防止 AI 忘记停止录制，让「正在调试」提示条一直挂着。被否：录制不设上限。 |
| 5 | 每个标签页缓存最多 1000 条控制台记录和 1000 个网络请求，满了丢弃最旧的，并在结果里报告丢弃数量。 | daemon 内存有界；1000 条足够覆盖一次复现。被否：不设上限，长时间录制会让 daemon 内存无限增长。 |
| 6 | 命令行按操作提供 `sctl debug` 子命令，MCP 每个操作一个工具（`debug_*`）。 | 与第 3 期 `page_*` 的粒度一致。 |
| 7 | 调试数据保存在 daemon 进程的内存里，由第 3 期的页面自动化组件一并管理，不写盘。 | 与第 3 期的引用表、弹框状态一样只在 daemon 内存中；调试数据含凭据，不落盘。被否：写到数据目录，凭据会留在磁盘上。 |

## 目标选择

- 沿用第 3 期的规则：浏览器按「操作类」选择；所有命令接受 `--tab <tabId>` 和 `--browser`，MCP 工具对应可选参数 `tabId` 和 `browser`；未指定标签页时使用最后获得焦点的窗口中的激活标签页；指定的标签页不存在时返回 `NOT_FOUND`，退出码 3。
- 每条命令的结果都带上实际的 `tabId`。
- `debug` 命令不操作页面，所以标签页上有未处理的 JS 弹框时照常执行，不返回 `DIALOG_OPEN`。弹框打开期间 Chrome 取不到请求体和响应体（见[JS 弹框](#js-弹框)），`debug request` 对它们照常返回、写明原因。
- `debug` 命令与同一标签页上的页面命令共用第 3 期的串行规则。

### JS 弹框

真机验证与修正轮探针（Chrome for Testing 125 headless/headful 与 153 一致，证据在 `e2e/scratch/2026-10-04-browser-debugging/verify/` 与 `fix-probe/`，已 gitignore）显示：

- 弹框打开期间，`Network.getResponseBody`、`Network.getRequestPostData` 一直阻塞到弹框关闭；处理弹框的命令仍可用。
- sctl 附加着、弹框打开、随后断开调试器，这个弹框会变成「孤儿」：之后任何新的调试会话上，附加用的命令全部阻塞，处理弹框的命令回答「没有弹框」，附加时也收不到弹框事件；只有导航或重新加载能关掉它。第 3 期在这种状态下附加会卡满超时。

因此：

- **弹框期间取体：** `debug request` 在弹框打开时（包括取体途中弹框打开）不等待：详情照常返回，请求体、响应体一项为空并写明原因「页面有未处理的 JS 弹框」，退出码 0。关掉弹框后再查可以取到。
- **不留下孤儿弹框（改变第 3 期）：** sctl 自己断开调试器时，如果知道这个标签页上有未处理的弹框，先关闭（dismiss）它再断开。这覆盖 `page detach`、`page detach --all`、5 分钟空闲断开、扩展的兜底空闲断开，以及扩展与 daemon 断线（包括 daemon 退出）后扩展释放调试器。这改变了第 3 期「弹框不会被自动接受或关闭」的规则：只在 sctl 即将断开时才自动关闭，其余时候仍不自动处理。用户点提示条「取消」引起的断开不在 sctl 控制之内，仍可能留下孤儿弹框。
- **附加无响应时快速失败：** 附加标签页时，附加用的命令 5 秒内没有回应，就放弃这次附加并返回 `PAGE_UNRESPONSIVE`，退出码 3，说明页面没有响应、可能有之前留下的 JS 弹框，可以用 `page reload` 或 `page goto` 恢复；不再等满命令超时。页面命令和 `debug` 命令都适用。这时无法确认原因一定是弹框。

## 记录什么

**控制台记录**（`debug console` 的来源，三种合在一个列表里）：

- `console`：页面调用 `console.log/info/warn/error/debug` 等产生的消息，以及它们的级别。
- `exception`：未捕获的 JS 异常和未处理的 Promise 拒绝，级别为 `error`，附带调用栈的前几帧。
- `browser`：Chrome 自己报告的消息，例如 CSP 违规、资源加载失败。（真机探针显示，废弃 API 警告在 Chrome 125 和 153 上都不会送达，所以不在其中。）

每条记录包含：序号、时间、来源、级别、文本、产生位置（URL、行、列，有就给）、当时页面的 URL。

- 文本按 DevTools 的方式把参数拼成一行，对象显示为预览。单条文本超过 10,000 个字符时截断，并标记已截断。

**网络请求**（`debug network` 的来源）：

- 每个请求一条记录；重定向的每一跳各是一条，并指向上一跳。
- 摘要包含：序号（同时作为请求 ID）、方法、URL、状态码、资源类型、开始时间、耗时、传输大小、失败原因（失败时）、是否来自缓存。
- 详情（`debug request`）另外包含：请求头、请求体（有就给）、响应头、各阶段耗时、远端地址。
- 跨进程 iframe 里的控制台消息和网络请求同样记录，记录里写明所在 frame 的 URL。iframe 文档本身的请求记在父页面上。
- **跨进程 iframe 的早期请求：** 调试器附加期间新出现的跨进程 iframe，由 Chrome 先暂停，sctl 为它开启记录后立即放行，所以它加载时最早发出的请求也会被记录。这改变了第 3 期附加后处理新 iframe 的方式：每个被暂停的 iframe 都必须被放行，开启记录失败时也要放行，绝不让 iframe 卡住。附加时已经存在的跨进程 iframe，附加之前发出的请求不记录，与顶层页面相同。

**附加之前的事件：** 网络请求只从附加之后开始记录。控制台消息、异常和 `browser` 消息，Chrome 在附加时回放当前文档的一部分（见[真机探针的结论](#真机探针的结论)），回放的照常进缓存，时间早于本次附加开始的时间。每个结果都带上本次附加开始的时间，调用方据此知道记录从什么时候开始。

**单条过大的事件：** 单个调试事件超过扩展到 daemon 的单帧上限（4 MiB）时，扩展会整条丢弃它，例如页面打印一个 5 MiB 的字符串。这样的记录不会出现在缓存里。

## 缓存与生命周期

- **何时开始缓存：** 调试器附加到标签页的那一刻起，无论附加是由页面命令、`debug start` 还是 `debug` 查询引起。
- **导航：** 页面导航后缓存保留，像 DevTools 的「保留日志」；每条记录写明当时页面的 URL。
- **上限：** 见设计决策 5。结果里的 `dropped` 报告被丢弃的最旧记录数。
- **清空：** 以下任一情况清空这个标签页的全部缓存：调试器断开（空闲断开、`page detach`、标签页关闭、浏览器实例断开、daemon 退出、用户在提示条上点「取消」），或执行 `debug clear`。

## 录制

- **开始录制：**
  - *前提：* 目标标签页可以附加。
  - *操作：* `debug start [--tab N]`。
  - *结果：* 附加调试器（已附加则沿用），标签页进入录制状态。录制期间，第 3 期的 5 分钟空闲断开和扩展的兜底断开都不生效。对已在录制的标签页再次执行也成功，不清空缓存。
  - 无法附加的页面返回 `PAGE_NOT_AUTOMATABLE`，退出码 3。
- **停止录制：**
  - *操作：* `debug stop [--tab N | --all]`。
  - *结果：* 结束录制，缓存保留；之后按第 3 期的规则，5 分钟内没有新的页面命令或 `debug` 命令就断开，缓存随之清空。目标不在录制时也成功，只是什么都不做。
- **自动结束：** 设计决策 4：录制中的标签页连续 60 分钟没有任何 `debug` 查询，录制自动结束，之后同「停止录制」。每条 `debug` 命令都重新计时。
- **录制被打断：** 调试器因为标签页关闭、实例断开、daemon 退出或用户点提示条「取消」而断开时，录制随之结束，缓存清空。
- **`debug status [--tab N]`：** 列出这个浏览器里被 sctl 附加的标签页（指定 `--tab` 时只列这一个）：是否在录制、本次附加开始的时间、控制台和网络各有多少条、各丢弃了多少条、录制还剩多久自动结束。

## 查询

所有查询命令在目标标签页未被附加时会附加它（提示条随之出现），并返回附加时得到的内容。

- **`debug console`** `[--level debug|info|warning|error] [--source console|exception|browser] [--text 子串] [--after 游标] [--limit N]`
  - `--level` 表示「这个级别及以上」。`--text` 按子串匹配文本，不区分大小写。
  - 按时间先后返回。
- **`debug network`** `[--url 子串] [--method M] [--status 404|4xx|5xx] [--type document|xhr|fetch|script|stylesheet|image|font|media|websocket|other] [--failed] [--after 游标] [--limit N]`
  - `--failed` 只返回失败的请求（网络错误、被取消、被拦截），不包括 4xx/5xx 响应。
  - 按开始时间先后返回。进行中的请求也会出现，状态标为进行中。
- **`debug request <ID> [--body]`**
  - 返回这个请求的详情。ID 不存在或已被丢弃时返回 `NOT_FOUND`，退出码 3。
  - 请求体超过 1 MiB 时只返回前 1 MiB 并标记已截断。
  - `--body` 一并返回响应体：文本原样返回，二进制以 base64 返回；超过 1 MiB 时只返回前 1 MiB 并标记已截断，同时给出原始大小。扩展在浏览器里取回完整的响应体后先截断再回传，所以 Chrome 还保留着的响应体，无论多大都能拿到前 1 MiB。
  - Chrome 已不再保留响应体时，详情照常返回，响应体一项为空并写明原因，退出码仍为 0。这包括：页面已导航离开（导航之后之前所有请求的响应体都取不回）、请求进行中、请求失败、没有响应体、页面没有读取 fetch 的响应体、单个响应体超过 Chrome 的保留上限（约 20 MB）、页面有未处理的 JS 弹框（见[JS 弹框](#js-弹框)）。
- **`debug clear [--tab N]`**：清空缓存，不影响录制状态和附加。
- **分页与游标：**
  - `--limit` 默认 100，最多 1000。结果带 `hasMore`，表示在 `--limit` 之外还有符合条件的记录。
  - 结果带 `next` 游标。下次传 `--after <游标>` 只返回之后新增的记录。
  - 游标是不透明的字符串。游标不属于当前缓存时（缓存被清空、调试器重新附加、daemon 重启之后），从缓存开头返回，并在结果里标记 `cursorReset: true`。
- **结果的共同字段：** `tabId`、本次附加开始的时间、是否在录制、`dropped`，以及 `contentTrust: "untrusted-page-content"`。

**命令行输出：** 默认输出表格，`-o json` 输出完整结果。`debug request` 默认输出头和体的可读文本。还有更多记录时，在 stderr 提示用 `--after` 或更大的 `--limit` 继续。

**MCP：** 工具 `debug_start`、`debug_stop`、`debug_status`、`debug_console`、`debug_network`、`debug_request`、`debug_clear`，参数与命令行一致；描述是静态文本，页面内容只作为数据返回。

## 安全与隐私

- 持有控制令牌的进程可以读到被附加标签页的网络请求头和响应头（包括 Cookie、Authorization 等登录凭据）、请求体、响应体，以及控制台内容。这一点写进威胁模型，与第 2 期可读取全部 Cookie 的说明放在一起。
- 调试数据只存在 daemon 内存里，不写盘，调试器断开后即丢弃。
- 控制台文本、URL、头和体都由网页控制，只作为结构化数据返回，结果带 `contentTrust` 标记。

## 协议与权限

- 不新增浏览器权限，`minimum_chrome_version` 仍为 125。
- 扩展需要知道哪些标签页在录制，录制期间不对它们执行兜底空闲断开。
- 请求体和响应体由扩展在浏览器里取回并截断到 1 MiB 后再回传，不经通用 CDP 中转（通用中转只能整体回传，超过单帧上限就一个字节也拿不到）。
- 以上协议变化都是只供 daemon 调用的内部方法，先加进 `protocol.json`，再按对端生成代码；给 ScriptCat 的生成文件逐字节不变。
- 新命令经第 3 期的页面控制接口提供，不开放原始 CDP。

## 真机探针的结论

实现计划的第一个任务在隔离配置中用 Chrome for Testing 125.0.6422.141 和 153.0.8010.12 做了真机探针，两个版本结论一致，证据在 `e2e/scratch/2026-10-04-browser-debugging/probe/`（已 gitignore）。

- **附加前的回放：** 开启控制台记录时，Chrome 回放当前文档最近的控制台消息和异常，两者合计最多 1000 条，顺序和原始时间不变；开启浏览器消息记录时回放当前文档的 CSP 违规和资源加载失败。导航之前的文档不回放。
- **响应体：** 页面一旦导航，之前所有请求的响应体都取不回；清 HTTP 缓存不影响。Chrome 只能一次取回整个响应体，不能分段读取，所以截断必须在扩展里做（见[协议与权限](#协议与权限)）。
- **吞吐：** 1 万到 5 万条日志、500 个请求，事件全部送达，没有丢失；中转每秒约 2,000–3,500 个事件。5 万条日志要 14–25 秒才能全部到达 daemon，这期间页面命令慢 3–6 秒，仍在默认超时之内。超过 4 MiB 的单个事件会被整条丢弃；带很大请求体的请求在默认参数下也会因此丢失，所以记录网络时要限制事件里内联的请求体大小，完整请求体改为按需取回。
- **JS 弹框：** 见[JS 弹框](#js-弹框)。
- **跨进程 iframe：** 子会话要在自己的会话上开启记录才有事件。控制台消息和异常在开启时回放，不会丢；开启之前发出的网络请求会丢，只有让新 iframe 启动时先暂停、开启后再放行，才能收全。

## 不在本期范围

- 性能追踪、内存快照、断点与单步调试、代码覆盖率。
- WebSocket 的帧内容、Server-Sent Events 的消息内容。
- 拦截、修改、屏蔽请求。
- Service Worker 和 Web Worker 里的控制台与网络。
- 持续输出（`--follow`）。
- 原始 CDP 端点，属于第 5 期。

| 测试层 | 验证什么 | 可参照的现有测试 |
|---|---|---|
| Go 页面组件单元测试，连一个假的 CDP 对端 | 事件到控制台与网络记录的转换（三种来源、重定向链、跨进程 iframe、失败与缓存）；上限与丢弃计数；筛选；游标与 `cursorReset`；录制期间不空闲断开、停止后恢复、60 分钟无查询自动结束；新出现的跨进程 iframe 暂停后一定被放行（包括开启记录失败时）；断开与 `debug clear` 清空缓存；`debug request` 的 `NOT_FOUND` 与响应体截断、不可用（包括弹框期间与取体途中弹框打开）；sctl 断开前关闭已知的弹框；附加命令 5 秒无回应返回 `PAGE_UNRESPONSIVE` | `internal/daemon/page/manager_test.go`、`internal/daemon/page/network_test.go` |
