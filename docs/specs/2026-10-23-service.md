# 把 sctl serve 注册为用户级系统服务

<!-- File: docs/specs/2026-10-23-service.md -->

> Status: Draft
> Owner: sctl maintainers
> Last updated: 2026-10-23

**目标：** 用户用一条 `sctl service install` 把 `sctl serve` 交给本机的用户级服务管理器（macOS launchd、Linux systemd
用户实例、Windows 任务计划程序），登录后自动启动、崩溃后自动拉起，不再需要一个一直开着的终端。

**不可退化的约束：**

- `sctl serve` 在前台运行的行为不变；前端（`sctl mcp` 和 CLI 动词）仍然不会自己拉起 daemon。
- stdout 只属于 CLI；服务下运行的 daemon 也不向 stdout 写任何东西。
- 服务只装在当前用户名下，不需要管理员权限，不写系统级位置。

## 问题

1. **后台运行没有现成办法。** 已验证。`sctl serve` 只能在前台运行（`internal/cli/serve.go` 的注释：“命令始终在前台运行，
   生命周期由调用方管理”）。[architecture.md](../architecture.md) 和 [mcp.md](../mcp.md) 让用户“交给系统服务管理器”，
   但 mcp.md 明说“具体的服务管理器配置不在本指南范围内”。用户得自己写 plist、unit 或计划任务，还得知道要把
   `--data-dir`、`--listen-address` 原样带进去。
2. **手写的服务定义容易和 CLI 对不上。** 已验证。daemon 和 CLI 必须用同一个数据目录和监听地址
   （README “Every sctl process must use the same data directory and listener address”）。服务管理器启动的进程拿不到
   用户 shell 里的 `SCTL_DATA_DIR`，路径不一致时 CLI 读不到控制令牌。

## 角色与用户故事

1. 作为日常使用 sctl 的用户，我希望运行一条命令后 daemon 就一直在后台，开机登录也自动起来，这样不用每次开终端跑 `sctl serve`。
2. 作为用自定义数据目录或端口的用户，我希望服务自动沿用我当前的 `--data-dir` / `--listen-address`，这样 CLI 和 MCP 不用额外配置。
3. 作为升级了 sctl 的用户，我希望有一条命令让服务换上新二进制，这样不用手动找服务定义。

## 设计决策

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | 由 sctl 生成并注册服务定义，交给系统自己的服务管理器托管，sctl 不自己做守护进程。 | 用户决定（方案 A）。服务管理器负责登录自启和崩溃拉起。被否：`serve --detach` 自己脱离终端——重启后不在、也不会拉起；前端自动拉起 daemon——违背“前端不启动 serve”的设计。 |
| 2 | 只做用户级服务：launchd 的 LaunchAgent、systemd `--user`、Windows 当前用户登录时触发的计划任务。 | 浏览器扩展、数据目录和控制令牌都属于当前用户。被否：Windows 服务——跑在 SYSTEM 账户下，数据目录和令牌对不上；systemd 系统服务——需要 root。 |
| 3 | 不引入第三方服务库，三份定义模板和命令序列自己写。 | `kardianos/service` 在 Windows 上只支持系统服务，与决策 2 冲突；模板各几十行，生成函数是纯函数，容易测。 |
| 4 | 每个用户只有一个 sctl 服务，名字固定：launchd 标签 `com.scriptscat.sctl`、systemd 单元 `sctl.service`、计划任务 `sctl`。 | 一个用户一个 daemon 是常态。被否：按数据目录生成不同名字——命令要多一个参数，收益很小。 |
| 5 | 服务的命令行在安装时固化：二进制的绝对路径，加上本次调用实际生效的 `--data-dir`（转成绝对路径，来自参数或 `SCTL_DATA_DIR`）、`--listen-address`、非默认的 `--log-level`，最后是 `serve --service`。 | 服务管理器不继承用户 shell 的环境（问题 2）。 |
| 6 | 二进制路径优先用 `PATH` 里的 `sctl`，前提是它和当前进程是同一个文件；否则用当前进程的路径。 | Homebrew 的 `bin/sctl` 是指向带版本号目录的符号链接，固化解析后的路径会在 `brew upgrade` 删掉旧版本后失效。 |
| 7 | 服务的运行状态以“daemon 能不能连上”为准，不解析服务管理器的输出。 | `schtasks` 的状态文字随系统语言变化，`launchctl print` 的格式不保证稳定。能不能连上本来就是用户关心的事。 |
| 8 | 新增隐藏参数 `serve --service`：日志只写文件，不再同时写 stderr；在 Windows 上，进程是控制台唯一的进程时脱离控制台。 | 文件日志已按大小滚动；stderr 交给服务管理器后，launchd 的输出文件不滚动，重复写一份会无限增长。stderr 只剩 Go 运行时的崩溃信息。Windows 上计划任务启动控制台程序会弹出窗口，脱离后窗口关闭（登录时会闪一下）。被否：编译成 GUI 子系统——CLI 就没有控制台输出了；`conhost --headless`——未公开的参数。 |

## 命令

所有子命令只操作本机的服务管理器，不经过 daemon 的控制 API。出错时退出码 3，消息说明原因；`-o json` 输出结构化结果。

- **`sctl service install`**
  - 写入服务定义，启用并立即启动；已经装过时覆盖定义并重启（升级、换路径、换参数都用它）。
  - 还没装过、却已经有 daemon 在这个地址上能连上时拒绝：说明有一个服务以外的 daemon 在运行，先停掉它。
    否则新服务会因为端口被占用而反复重启。
  - 启动后最多等 10 秒让 daemon 能连上：连上时输出 daemon 地址；等不到时退出码 3，并给出日志目录。
  - 输出服务定义的位置和固化的命令行。
- **`sctl service uninstall`**：停止服务、取消登录自启、删除服务定义。没装过时也成功，并如实说明。
- **`sctl service start` / `stop` / `restart`**：启动、停止、重启已安装的服务。没装过时退出码 3，提示先 `install`。
  `start`、`restart` 和 `install` 一样等 daemon 能连上。`stop` 后服务在下次登录时仍会自动启动。`start` 时已经有 daemon
  能连上就什么都不做（它要么就是服务，要么是占着端口的前台 daemon，再启动服务只会反复重启）。
- **“等 daemon 能连上”的判定：** 能回答健康检查，且本数据目录的控制令牌与操作前不同。daemon 绑定端口后才写新令牌，
  令牌变了才说明是服务新启动的进程；只看健康检查会把占着端口的别的 daemon 当成服务已启动。
- **“已有 daemon”的判定（install、start 前）：** 只看健康检查，不要求本数据目录有令牌，另一个数据目录的 daemon 同样占着端口。
- **`sctl service status`**：是否已安装、服务定义的位置、daemon 当前能不能连上。没装过时退出码 0，如实说明。固化的命令行只在 `install` 时输出：读回 Windows 计划任务的定义要解析随系统语言变化的输出，不值得。

不支持的系统（三种之外）上，所有子命令退出码 3，说明不支持。

## 各平台的服务定义

| 平台 | 位置 | 要点 |
|---|---|---|
| macOS | `~/Library/LaunchAgents/com.scriptscat.sctl.plist` | `RunAtLoad`；不设 `ProcessType=Background`（会被系统节流，而 daemon 服务的是交互请求）；`KeepAlive` 只在非正常退出时拉起；stdout 指向 `/dev/null`，stderr 写 `<数据目录>/logs/service.stderr.log`。用 `launchctl bootstrap` / `bootout` / `kickstart` 管理 `gui/<uid>` 域。 |
| Linux | `$XDG_CONFIG_HOME/systemd/user/sctl.service`（默认 `~/.config/systemd/user/`） | `Restart=on-failure`、`RestartSec=5`、`WantedBy=default.target`；按单元文件的绝对路径 `enable`（调用者 shell 与 systemd 用户实例的 `XDG_CONFIG_HOME` 可能不同）；stderr 由 journal 接收。用 `systemctl --user` 管理。用户服务只在用户登录期间运行，这与浏览器的生命周期一致。 |
| Windows | 计划任务 `\sctl`，定义保存在任务计划程序里 | 当前用户登录时触发、以当前用户的交互令牌运行、不需要提权；取消默认的 72 小时运行上限和电池相关的停止条件；失败后每分钟重试、最多 999 次（任务计划程序的 `RestartOnFailure`；它是否覆盖进程以非零码退出，未在真机上确认）；已在运行时 `/Run` 先停掉旧实例再启动（`StopExisting`），重启与覆盖安装都靠它，不先 `/End` 再赌时序。用 `schtasks /Create /XML`、`/Run`、`/End`、`/Delete`、`/Query` 管理。 |

macOS 上 launchd 启动的进程没有隐私授权时读不了 `~/Documents`、`~/Desktop`、`~/Downloads`，会卡住而不是启动
（真机验证中二进制放在 `~/Documents` 下时复现：进程在运行，但既不监听也不写日志）。文档提示把二进制和数据目录放在这些目录之外。

服务定义中的路径和参数按各自格式转义（plist 和任务 XML 按 XML 转义，systemd 按 `ExecStart` 的引号与 `%` 规则）。

## 安全与隐私

- 服务定义里只有二进制路径、数据目录、监听地址和日志级别，不含密钥或令牌。定义文件写在当前用户的目录里，
  能改它的人本来就能以这个用户身份运行程序，因此不进入[威胁模型](../threat-model.md)的凭据清单。
- daemon 在服务下运行时的监听地址与前台运行相同（默认 127.0.0.1），威胁模型不变。

## 不在本期范围

- `serve --detach` 和前端自动拉起 daemon（决策 1）。
- 系统级服务、Windows 服务（决策 2）。
- Homebrew 的 `brew services`：需要改外部的 tap 仓库；与 `sctl service` 同时使用会争同一个端口，文档提示二选一。
- 同一用户装多个 sctl 服务（决策 4）。
